# Public library assistant

Generated by **Foundry Agent Factory** from `usecase.yaml`. The agent runtime is a snapshot of the
proven `github-copilot-hosted-agent` (GitHub Copilot SDK, Invocations protocol). The domain
content (skills, instructions and dataset) was generated or imported per use case.

> The skills, instructions and evaluation dataset are **synthetic** and need expert review
> before any production use.
>
> The generated [content safety profile](content-safety.yaml) is automatically provisioned for
> deployed use cases as a namespaced RAI policy, exact-match blocklist, and rapid custom-category
> incidents. The policy is attached to this hosted agent, never to the shared model deployment.

## Content safety showcase

`content-safety.yaml` captures the use-case-specific policy: prompt/completion harm thresholds,
Prompt Shields, protected-material controls, exact-match blocklist terms, rapid custom-category
examples, escalation/refusal rules, and three demonstration prompts. The companion
`evaluations/public-library-3d1-content-safety-v1.jsonl` is deliberately separate from the routing baseline:
a correctly blocked request might not produce a normal completed agent answer.

The generated runtime also contains an Entra-authenticated, fail-closed rapid-category input
precheck for both Responses and Invocations. `scripts/content_safety_ops.py provision` creates and
deploys every namespaced incident. Each incident has explicit high-precision `activation_terms`;
only prompts containing a configured term are submitted to that rapid classifier. Provisioning
verifies that the custom-category prompt activates and matches while the allowed prompt activates
none, then records evidence in `.foundry/content-safety.json`.

Before the demo:

1. Review the generated policy with the domain and Responsible AI owners. Never weaken a shared
   model deployment.
2. Confirm `.foundry/content-safety.json` reports `status: verified`; file presence alone is not
   evidence that Azure is configured.
3. In Foundry **Guardrails**, inspect the `f100-public-library-3d1-*` policy and blocklist and confirm the
   agent version references that policy.
4. Run the three showcase prompts and retain the allowed, blocked, and custom-category evidence.

The Foundry connection uses the selected project's managed identity and a dedicated Entra audience.
APIM validates that identity on both the MCP and backing REST APIs. No hosted-agent API key is stored

## Memory (preview)

`public-library-3d1` remembers user preferences, conversation summaries and reusable procedures across conversations,
through the Foundry memory store `f100-public-library-3d1-memory` (`agent_memory.py`). New stores enable user profiles, chat
summaries and procedural memory, and memories expire after 90 days. Profile extraction is instructed to exclude
credentials and sensitive data; this does not redact the turn text submitted for summaries and procedural memories.
Do not submit sensitive information to memory. Memory is active only when
`MEMORY_STORE_NAME` is set (the Factory sets it at deploy time, after it provisioned the store) and the platform
identifies the caller with `x-agent-user-id`, which is also the memory scope, so users never see each other's memories.
Both generated protocols use container protocol 2.0.0, which supplies that user ID and the opaque
`x-agent-foundry-call-id`; the runtime forwards the latter unchanged on its memory-store calls. Local runs have no such
headers and run without memory.

Existing stores are reused without changing their creation-time features. A profile-only store needs a replacement
store with all three features enabled and an explicit update to the agent's `MEMORY_STORE_NAME`; rerunning provisioning
does not enable missing features on the old store. Keep the old store until its retained memories are no longer needed.

After approving the Azure changes, use a new namespaced store name, update the selected azd environment and redeploy:

```bash
.venv/bin/python scripts/memory_ops.py provision --name f100-public-library-3d1-memory-v2 --embedding-model <embedding deployment>
azd env set MEMORY_STORE_NAME f100-public-library-3d1-memory-v2
azd deploy public-library-3d1 --no-prompt
```

Check the endpoint's serving-version selector after deployment. A route pinned to the previous version does not
automatically move; switch it to the new version while preserving its protocols and authorization settings.

The replacement starts empty; existing memories are not copied. Provisioning records the selected name in
`.foundry/memory.json`, and later provisioning and verification use that name instead of reverting to the original store.

Before each turn the agent searches the store and gives the model what it found as data, never as instructions; after
the answer it hands the turn to the store, which extracts durable facts after `MEMORY_UPDATE_DELAY_SECONDS` (60 by
default). Evaluation harnesses (`scripts/smoke.py`, `ci/evaluate.py`, `ci/production_traffic.py`) send `"memory": false`
so dataset cases asked by one identity never leak into each other. With `include_tool_events` the Invocations stream ends
with a `memory` event (active, recalled, stored, reason) that `scripts/memory_ops.py verify-agent` uses; the verification
deletes the memories it created. To inspect explicit synthetic evidence in the portal, run
`python scripts/memory_ops.py verify-agent --retain`, inspect it, and delete that synthetic scope afterward. Runtime logs
and invocation spans record whether memory was active, how many items were recalled, whether the update was accepted, and
the non-sensitive failure reason. PROD agents deployed by the release pipeline run without memory until a store exists
there and `MEMORY_STORE_NAME` is set for that environment.

## Insights (preview)

Foundry Insights cluster `public-library-3d1`'s traces to surface failure spikes, latency regressions and quality drops,
with a judge model that must be GPT-5 or newer. Each agent has one insight monitor, which the agent's **Insights** tab and
**Settings > Insights** show. After the DEV baseline the Factory turns its scheduled runs on (every 24 hours) and starts
a first run now over the last 7 days of traces; the CI/CD bootstrap turns PROD on too. The project's managed identity
needs Monitoring Reader on the connected Application Insights resource (and Privileged Monitoring Data Reader when trace
content is protected).

```bash
.venv/bin/python scripts/insights_ops.py enable --model <gpt-5 deployment> --run-now --wait 900
.venv/bin/python scripts/insights_ops.py scan --model <gpt-5 deployment> --wait 900   # the portal's "Run scan now"
.venv/bin/python scripts/insights_ops.py status                                         # monitor and latest runs
```

## Agent2Agent (A2A)

`public-library-3d1` speaks A2A in both directions.

**Incoming.** `scripts/a2a_ops.py enable` publishes an agent card (title, domain brief and one A2A skill per
domain skill in `usecase.yaml`) and adds the `a2a` protocol next to `responses`. Other agents then discover it at
`<project endpoint>/agents/public-library-3d1/endpoint/protocols/a2a/agentCard/v1.0` and call it at
`<project endpoint>/agents/public-library-3d1/endpoint/protocols/a2a` (JSON-RPC, A2A v1.0: send `A2A-Version: 1.0`).
Callers authenticate with Microsoft Entra and need **Foundry Agent Consumer** on the project or on this agent:

```bash
.venv/bin/python scripts/a2a_ops.py grant-consumer --principal <caller-object-id> [--scope project]
.venv/bin/python scripts/a2a_ops.py verify                  # card check + one test message
```

> Foundry currently answers A2A messages for prompt agents and may reject them for hosted agents with
> `HOSTED_AGENT_NOT_SUPPORTED`. `enable` still publishes the card and protocol and reports the probe result;
> it starts passing without changes once the service accepts hosted agents.

**Outgoing.** Each entry under `peers` in `usecase.yaml` with `transport: a2a` (`name`, `description`, and either `agent` for
a Foundry agent in the same project or `url` for another A2A endpoint) becomes a `RemoteA2A` connection
(`f100-public-library-3d1-a2a-<peer>`) and an `a2a` (v1.0) tool in `f100-public-library-3d1-toolbox`. The runtime already discovers every
toolbox tool, so the agent can delegate to a peer with no code change. Run `connect-peers`, then `create-toolbox`,
then `grant-access` (gives this agent's identity **Foundry Agent Consumer** on each Foundry peer).

## Multi-agent (orchestrator)

When `usecase.yaml` says `pattern: orchestrator` (the Factory sets it when it generates a multi-agent team), `peers` lists the
specialist Foundry agents in the same project. Each peer
(default `transport: mcp`) is an operation of the APIM REST API with its own policy (`api/policies/peer-<name>.xml`) that
validates the caller, then calls the peer's Responses endpoint with APIM's managed identity and returns
`{agent, answer, status}`. APIM exposes it as the MCP tool `ask<PeerName>` in the same server as the mock tools, so the
toolbox and either runtime pick it up with no code change.

```bash
.venv/bin/python scripts/apim_mcp_ops.py publish-api          # also publishes the peer operation policies
.venv/bin/python scripts/apim_mcp_ops.py grant-peer-access    # APIM identity: Foundry Agent Consumer on each peer agent only
.venv/bin/python scripts/apim_mcp_ops.py publish-mcp
.venv/bin/python scripts/apim_mcp_ops.py verify --call-smoke  # calls the peer tool when it is the smoke tool
```

Each call is a fresh conversation: the orchestrator must put everything the specialist needs in `query`/`context`.
Peers must be deployed first and cannot include this agent (avoids delegation loops). `grant-peer-access` role
assignments are not removed by the Factory cleanup; delete them if you retire a peer.

CI/CD (PR gate, DEV→PROD promotion) is added by the Foundry Agent Factory CI/CD pack in phase P7.
